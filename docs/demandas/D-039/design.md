# D-039 (E1.4) — Convite de profissional: desenho

## 1. Resumo e alternativas
Gestor convida (`convidarProfissional`, serve também para reenviar); o link `/convite/<token>` abre uma página pública que só verifica no GET e, no POST (Server Action, funciona sem JS), cria o `usuario` e o vínculo numa transação. Sem login automático.
Descartadas: (a) reutilizar a tabela `token`/`tipo_token` (o `convite` já existe, com FK composta ao profissional e e-mail próprio); (b) criar o usuário no envio (usuário sem senha vira alvo de login/recuperação); (c) aceite dentro de `defineAcao` (não há sessão; seria 401); (d) travar `usuario` antes do profissional (viola a ordem canônica); (e) novo `papel`/operação de matriz: reutiliza-se `'profissional.gerir'`; (f) web-designer dispensado: tela análoga a `/redefinir-senha` com os mesmos componentes e CSS; (g) Turnstile no aceite: a posse do token basta (spec §7).

## 2. Componentes (caminhos)

Reusa `FORMATO_TOKEN`, `esquemaEmail`, `enviarEmailDeConfirmacao` (envio sem lançar), `gerarToken`, `hashDoToken`, `gerarHashSenha`.
- `src/server/convites/` (gestor, tenant): `tipos.ts` (client-safe: `EntradaConvidar`, `ResultadoConvidar`, `EstadoConvite`, textos), `servico.ts` (`convidar(ctx, e, agora, deps?)`, `estadoDosConvites(ctx, ids)`), `convites.acao.ts` (`convidarProfissional = defineAcao({ papeis: ['gestor'], capacidade: 'configurar' }, (ctx, e, { agora }) => servico.convidar(ctx, e, agora))`; `exigirPermissao(ctx,'profissional.gerir')` no serviço).
- Repos: `src/server/repos/convite.ts` (tenant-escopado, `Repos.convites`, registrar em `repos/index.ts`/`tipos.ts`): `travarProfissionalParaConvite` (`SELECT … FROM profissional … FOR NO KEY UPDATE OF p`, devolve `ativo`, `email`, `usuario_id`), `emailEmUso(email)` (leitura simples `lower(email)`), `invalidarPendentes`, `inserir`, `contarEnvioNaJanela(tx)` (incremento de `rate_limit_janela` na própria transação), `ultimoPorProfissional(ids)` (só estado/datas, nunca `token_hash`). `src/server/repos/convite-publico.ts` (PRÉ-CONTEXTO, exceção como `token-recuperacao.ts`; só recebe hash): `buscarConvitePorHash` (leitura sem trava, sem escrita), `aceitarConvitePorHash`.
- Edição de e-mail: `src/server/profissionais/servico.ts#editar` e `repos/profissional.ts#atualizarDados` passam a invalidar convites pendentes se o e-mail mudou, na mesma transação (RN-7; a trava `FOR UPDATE`/`NO KEY UPDATE` já existe).
- Telas: `src/app/(publico)/convite/[token]/{page.tsx,FormularioConvite.tsx,FormularioConvite.module.css,acoes.ts,estado.ts}` (cópia estrutural de `redefinir-senha`: um client component único decide formulário/recusa/sucesso, o estado da action vence o veredito da página; `page.tsx` `dynamic = 'force-dynamic'`, só GET de leitura). Painel: `src/app/painel/profissionais/ConviteProfissional.tsx` (+`.test.tsx`, botão "Enviar convite"/"Reenviar convite", estado: sem convite, pendente até DD/MM, expirado, aceito, via `format.ts` no fuso do salão), `src/app/painel/profissionais/acoes.ts` ganha o shell `convidarAcao` (única edição do shell), `[id]/page.tsx` renderiza o componente (`useActionState` por ação em ordem fixa). Lista (`ListaProfissionais.tsx`) mostra o selo do estado. Vitrine: `src/app/dev/convite/` (404 fora de `VITRINE_COMPONENTES=true`/`next dev`, ação só de validação, `ROTAS.devConvite`).
- `next.config.ts`: `source: '/convite/:token'` com `Referrer-Policy: strict-origin`, `Cache-Control: no-store`, `X-Robots-Tag: noindex` (mesmo bloco do convite de avaliação). `/convite` já é reservado; o proxy só cobre `/painel` e `/admin`, nada a mudar.

## 3. Interfaces
- `convidar` resultados (dentro de `{ ok: true, dados }`): `criado { emailEnviado, expiraEm }` | `invalido { erros: { email?, formulario? } }` (sem e-mail no perfil, e-mail em uso, já tem acesso, inativo) | `limite`. Id malformado/de outro salão = `NaoEncontrado`.
- `aceitarConvite` → `aceito` | `recusado` (uma única mensagem, motivo só em log `auth.convite` sem dados pessoais) | `invalido {senha}` | `falha`. `verificarConvite` → `valido | recusado`.
- Fluxo `convidar` (uma transação READ COMMITTED): `profissional FOR NO KEY UPDATE` (recusas RN-3/5/6) → `emailEmUso` (RN-4; mensagem única) → `invalidarPendentes(agora)` → `INSERT convite` (e-mail minúsculo do perfil) → incremento da janela; contador > 3 lança sentinela `DesfazerConvite` capturada fora (rollback também do convite novo e da invalidação; só convites emitidos contam). Depois do commit: envio síncrono via `integracoes().email` (try; falha → `emailEnviado: false`, log sem token). Token em claro só na memória.
- Fluxo aceite: validar a senha (sem consultar o banco) → hash argon2 fora da transação → lookup sem trava do convite pelo hash (acha `profissional_id`; ausente = `recusado`) → transação: `profissional FOR UPDATE` (serializa com desativar/reenviar/editar) → `convite FOR UPDATE` (relido) → confere `aceito_em`/`invalidado_em` nulos, `agora < expira_em`, profissional `ativo` e `usuario_id IS NULL`, `convite.email` = `profissional.email` normalizado → `INSERT usuario … ON CONFLICT (email) DO NOTHING RETURNING id` (0 linhas = e-mail em uso → rollback, recusa) → `UPDATE profissional SET usuario_id` → `UPDATE convite SET aceito_em`. Nunca captura 23505. Sem sessão, sem cookie.
- Ordem de travas (a registrar no cabeçalho de `repos/convite.ts`): `salao` (se usado) → `profissional` → `convite` → `usuario` → `rate_limit_janela`. Reenvio × aceite: o `FOR UPDATE` do aceite conflita com o `FOR NO KEY UPDATE` do envio; o perdedor relê o estado: aceite vence → reenvio vê `usuario_id` e recusa "já tem acesso"; reenvio vence → o aceite do link antigo vê `invalidado_em` e recusa (CA-6/7/8).

## 4. Dados
Nenhuma coluna/tabela. Migração opcional de segurança: `CREATE UNIQUE INDEX convite_pendente_por_profissional_uniq ON convite (profissional_id) WHERE aceito_em IS NULL AND invalidado_em IS NULL;` — **DBA: sim, parecer curto** (índice parcial único com linhas vencidas: vencido-não-invalidado ainda conta como pendente, por isso `convidar` sempre invalida antes de inserir e o desativar já invalida; confirmar que não quebra dados existentes, impacto no `ON CONFLICT`, reversão `DROP INDEX`; e a ordem do `schema.prisma`, que não expressa o parcial). Sem ele o desenho já é correto pela trava do profissional; é só cinto. Tarefa T-2 do DBA, T-3 depende dela só nos testes de unicidade.

## 5. Infraestrutura
**DevOps: não.** Sem variável nova (`APP_URL`, `EMAIL_ADAPTER` existentes), sem container/CI novo. O `docker/smoke.sh` ganha uma linha (`/convite/x` com `referrer-policy: strict-origin`), que a T-6 faz (arquivo sob posse do desenvolvedor, trivial).

## 6. Invariantes
- Escopo por salão no servidor: `convidar` por `defineAcao` + `RepoConvite` escopado, id de outro salão = 404; o aceite deriva `salao_id` do convite (nunca da entrada). Aplica-se.
- Exclusion constraint: não se aplica (RN-15, não toca `reserva`).
- UTC: `expira_em = agora + 7 × 24 h` por instante; exibição por `format.ts` no fuso do salão (testes em UTC e America/Sao_Paulo).
- Adaptadores: e-mail só por `integracoes().email`. Sem Turnstile/MP/WhatsApp.
- Soft delete: aceite não remove nada; desativar já invalida; reativar não restaura.
- Suspenso: `convidar` segue a política D-038 (`configurar` bloqueado); aceite é pré-contexto e permitido.
- Idempotência: token de uso único via travas; envio duplicado só pelo gestor, limitado a 3/15 min.
- Auditoria super admin: não se aplica. Anti-enumeração: aceite uniforme; `GET` não grava; o gestor vê "e-mail em uso" (risco aceito, limitado pelo RN-12).

## 7. Riscos
R-1 `ON CONFLICT DO NOTHING` + corrida: mitigado pelas travas e teste de 10 repetições. R-2 limite contado dentro da tx: reverte em recusa (desejado). R-3 e-mail do perfil com caixa/espaços: normalizar na leitura (`normalizarEmailOpcional`). R-4 vazamento do token por Referer/cache: headers da rota + link com `APP_URL`. R-5 convite vencido-não-invalidado mantém o índice parcial ocupado: invalidar sempre antes de inserir. R-6 e-mail trocado no perfil depois do envio: invalida (RN-7) e o aceite confere.
